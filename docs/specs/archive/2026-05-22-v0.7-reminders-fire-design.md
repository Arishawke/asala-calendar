# Design: v0.7 reminders fire from Asala

Status: Draft (not yet implemented).
Target release: v0.7.0. First slice of M4 (the "reminders fire"
milestone). Subsequent slices: trash bin (v0.8.0), drag-to-reschedule
(v0.9.0).

## Context

Through v0.6.0, Asala writes reminders to
`CalendarContract.Reminders.METHOD_ALERT` but does not fire them. The
provider's `METHOD_ALERT` is delivered by whichever sync adapter owns
the calendar's account, which in practice means some other calendar
app fires the alarm and posts the notification on Asala's behalf.
Users on devices without one of those sync adapters set up, for
example a local-only Asala calendar created from the drawer in v0.6,
or a CalDAV calendar synced via DAVx5 (which does not implement
reminder firing), see no notifications at all. Users on devices where
another calendar app IS the firer get duplicate or confusing reminder
behaviour when Asala is installed alongside it.

This slice makes Asala fire its own reminders via `AlarmManager`,
post its own notifications, handle snooze, and survive the standard
mobile-OS edge cases (reboot, time-zone shift, app upgrade, doze,
OEM background killers).

## Goal

A reminder set in Asala fires from Asala on schedule, on any Android
13+ device, regardless of which sync adapter (or none) owns the
calendar.

Secondary goal: make the permission and reliability story explicit
and recoverable. Users who decline notification permission must see
that fact and know how to enable it later. Users on aggressive OEMs
(Samsung, Xiaomi, OnePlus, Huawei, Oppo, Vivo) must be told their
phone may kill us in the background, with a one-tap path to the
right battery settings screen.

## Explicit non-goals

- Multi-reminder UI in the event editor. The scheduler reads ALL
  reminder rows for an event from the provider, so when the editor
  gains a multi-reminder picker later, no scheduler changes are
  needed. The editor stays single-reminder in v0.7.
- "Treat as alarm" / louder-than-default channel. Slice 1 ships one
  channel at `IMPORTANCE_HIGH` (heads-up). Loud-as-alarm-clock is a
  separate feature, deferred.
- Full-screen / lockscreen-takeover reminders. Anti-pattern per user
  feedback; opt-in if ever added.
- Per-account default reminder values.
- Email reminders.
- Location-based snooze.
- "Mark done" notification action. Waits for a Tasks-style feature.
- Drag-to-reschedule (separate slice).
- Trash bin (separate slice).

## Prior art consulted

- **Permission ladder** (the reference pattern from open-source
  Android calendars): `USE_EXACT_ALARM` unconditional,
  `SCHEDULE_EXACT_ALARM` with `maxSdkVersion="32"`,
  `setExactAndAllowWhileIdle` for scheduling, inexact
  `setAndAllowWhileIdle` fallback when exact is denied on Android 12.
  A common snooze design is one Settings-default-minutes value or a
  pick-each-time activity, gated by a toggle. We borrow the ladder;
  we replace the toggle with a picker that always shows on first
  snooze of a session.
- **Snoozed-alarm persistence**: the pattern via
  `CalendarContract.CalendarAlerts` row writes (`STATE_FIRED` →
  `STATE_SCHEDULED` transition, re-arm on AlarmManager). Survives
  process death. AOSP-blessed.
- **No in-app snooze** (system-swipe only) is a long-running user
  complaint about some calendar apps. We do better.
- **dontkillmyapp.com**: the OEM background-kill list. Drives our
  one-time advisory copy and deep-link targets.
- **Canonical reminder failure modes**: recurring instance fires for
  wrong date, repeated firing of same alert, random late firing for
  past events, all-day DST shift. All four are explicit cases in the
  testing strategy below.

## What changes for the user

### First time a reminder is saved

1. User opens the event editor, sets a reminder offset other than
   "None", taps Save.
2. If `POST_NOTIFICATIONS` not yet granted: in-app rationale dialog
   appears before the system prompt. Text: *"Asala needs to post
   notifications to ring your reminders. Without this, the reminder
   saves but won't alert you."* Buttons: *Continue* (fires the
   system prompt) and *Not now* (skips it).
3. If user taps *Continue*: standard Android 13+ system prompt
   fires. Save proceeds either way.
4. If user denies (either via *Not now* or system prompt deny):
   - The reminder still saves to the provider.
   - Event detail sheet renders a persistent yellow banner:
     *"Notifications are off. This reminder won't ring."* with a
     *Turn on* button.
   - Settings screen gains a similar banner in its Notifications
     row.
   - *Turn on* re-launches the system prompt if it is re-promptable,
     otherwise deep-links to the app's system Notifications settings
     screen.

### When a reminder fires

Notification content:
- Title: event title (or localized "(no title)" fallback).
- Body line 1: time range, e.g. "9:00 - 10:00 AM", or "All day".
- Body line 2 (only if present and non-empty): location.
- Description is NOT included (too long for a notification).
- Left side: 4dp vertical color stripe in the calendar's color.
- Tapping the body opens the event detail sheet in Asala (deep
  link via `MainActivity` with an event-detail intent extra).

Notification actions:
- **Snooze** (left action).
- **Dismiss** (right action).

### Snooze flow

- First snooze tap of the current app process opens a bottom sheet
  in a trampoline activity (`SnoozePickerActivity`). Options:
  5 / 10 / 15 / 30 minutes / 1 hour / Custom. The currently selected
  default (initially the Settings value, default 10) is highlighted.
- Picking a value:
  - Writes a new `CalendarAlerts` row for the same event with
    `BEGIN = now + chosen_minutes * 60 * 1000` and
    `STATE = STATE_SCHEDULED`.
  - Marks the original `CalendarAlerts` row as `STATE_DISMISSED`.
  - Schedules a new `AlarmManager.setExactAndAllowWhileIdle` for
    the new alert time.
  - Updates the in-process "session snooze choice" cache.
  - Dismisses the original notification.
- Subsequent snooze taps in the same app process use the cached
  choice directly (one tap, no picker).
- The session cache resets at app process death. Across cold-start
  sessions, the picker re-shows on the next snooze, pre-selected to
  the Settings default.
- Custom picker is a Material 3 time-duration picker capped at 24h.

### OEM battery-killer advisory (one-time)

On first launch after upgrade to v0.7.0, if `Build.MANUFACTURER`
matches one of Samsung, Xiaomi, OnePlus, Huawei, Oppo, Vivo
(case-insensitive), show a one-time dialog:

> *"Some phone brands aggressively close background apps to save
> battery. This can stop Asala from firing reminders on time.
> Tap below to allow Asala to run in the background, or skip if
> you're confident your phone won't kill us."*
>
> Buttons: *Open battery settings* | *Skip*

*Open battery settings* fires a manufacturer-specific intent (see
deep-link table in implementation notes). *Skip* sets a one-shot
DataStore flag (`oemAdvisoryShown = true`) so the dialog never
appears again on this install. The dialog is also accessible from
Settings > Notifications > "Background reliability" for users who
skipped.

### Settings additions

Settings screen gains a new section "Notifications", above the
existing "Sync" section:

- **Notifications status row.** Shows "On" or "Off — tap to enable."
  Tapping when off re-runs the permission flow.
- **Default snooze duration.** Dropdown: 5 / 10 / 15 / 30 min /
  1 hour. Default 10. Persisted to DataStore Preferences. Seeds
  the `SnoozePickerActivity` selection.
- **Background reliability** (only shown if OEM is in the affected
  list). Re-launches the OEM advisory dialog.

## What stays the same

- Event editor's reminder dropdown UI: unchanged. Single reminder
  per event remains in v0.7.
- All views (Month, Week, Day, Schedule): unchanged.
- The drawer, the search screen, the create-local-calendar dialog:
  unchanged.
- The Calendar Provider write path for reminders
  (`RemindersRepository.setReminder`): unchanged. The scheduler
  reacts to provider changes via `ContentObserver`.

## Architecture

New components, all under `app/src/main/kotlin/com/arishawke/asala/calendar/notifications/`:

| File | Responsibility |
|---|---|
| `ReminderScheduler.kt` | Reads upcoming events with reminders within a rolling 30-day window. Schedules `AlarmManager` `PendingIntent`s via `setExactAndAllowWhileIdle()`. Cancels stale alarms when reminders are removed. Public entry point used by every reschedule trigger. |
| `ReminderAlarmReceiver.kt` | `BroadcastReceiver` for fired alarms. Reads event via repository, posts notification, updates the `CalendarAlerts` row to `STATE_FIRED`. |
| `NotificationActionReceiver.kt` | `BroadcastReceiver` for the Snooze and Dismiss action intents. Snooze: if session-cached value exists, snooze directly; else, launch `SnoozePickerActivity`. Dismiss: cancel notification + mark `CalendarAlerts` row `STATE_DISMISSED`. |
| `SnoozePickerActivity.kt` | Translucent trampoline activity (no UI chrome) that renders a Material 3 modal bottom sheet with snooze options. On selection, fires a `PendingIntent` back to `NotificationActionReceiver` with the chosen minutes as an extra; the receiver does the `CalendarAlerts` writes and `AlarmManager` rescheduling. Activity finishes immediately after. |
| `BootRescheduler.kt` | `BroadcastReceiver` listening on `BOOT_COMPLETED`, `LOCKED_BOOT_COMPLETED`, `MY_PACKAGE_REPLACED`, `TIMEZONE_CHANGED`. Re-runs `ReminderScheduler.rescheduleAll()`. |
| `NotificationChannelInitializer.kt` | One channel: id `"reminders"`, name "Event reminders" (localized), `IMPORTANCE_HIGH`. Initialized on `Application.onCreate`. |
| `OemBatteryAdvisory.kt` | OEM detection via `Build.MANUFACTURER` allow-list. Deep-link intent helpers per manufacturer (see implementation notes). One-shot DataStore flag. |
| `ReminderTimeMath.kt` | Pure functions: all-day reminder shift to 09:00 local, recurring next-instance arithmetic. Unit-testable on the JVM, no Android dependencies. |

Existing modifications (small):
- `AndroidManifest.xml`: add `USE_EXACT_ALARM`, `SCHEDULE_EXACT_ALARM` with `maxSdkVersion="32"`, `RECEIVE_BOOT_COMPLETED`. Declare the four receivers and the trampoline activity.
- `AsalaCalendarApplication.kt`: invoke `NotificationChannelInitializer` on create. Trigger `ReminderScheduler.rescheduleAll()` once on app foreground (idempotent safety net).
- `EventEditViewModel.kt`: on save when a reminder is set and permission not yet granted, raise a one-shot UI event consumed by the editor to show the rationale dialog.
- `SettingsScreen.kt`: add the new Notifications section.
- `MainActivity.kt`: handle the `notif_open_event` intent extra to deep-link into event detail.
- `AppViewModel.kt`: expose `notificationPermissionGranted: StateFlow<Boolean>` so the editor and settings can react.
- New `data/PreferencesRepository.kt` field for `defaultSnoozeMinutes` (Int, default 10) and `oemAdvisoryShown` (Boolean, default false).

### Permission ladder

```xml
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
<uses-permission android:name="android.permission.USE_EXACT_ALARM" />
<uses-permission android:name="android.permission.SCHEDULE_EXACT_ALARM"
    android:maxSdkVersion="32" />
<uses-permission android:name="android.permission.RECEIVE_BOOT_COMPLETED" />
```

`USE_EXACT_ALARM` is the primary path (Android 13+, install-time
grant, not user-revocable, calendar-app carve-out in Google Play
policy). `SCHEDULE_EXACT_ALARM` is declared only up to API 32 so
Android 12 still has a path; on Android 12 it requires the user to
grant in Settings, and we fall back to inexact
`setAndAllowWhileIdle` if denied. Both paths suppress reminders by
no more than a few minutes worst-case on Android 12; on 13+ they
fire precisely.

Deliberately NOT requested:
- `FOREGROUND_SERVICE` — no service is needed; `AlarmManager` +
  `BroadcastReceiver` is enough.
- `WAKE_LOCK` — `setExactAndAllowWhileIdle` handles wake.
- `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` — over-permission per
  the prior-art audit. We use the OEM-deep-link approach instead.

### Reschedule triggers (priority order)

1. `ContentObserver` on `CalendarContract.Events.CONTENT_URI` and
   `CalendarContract.Reminders.CONTENT_URI`. Instant re-schedule
   when an event or reminder is created, edited, or deleted.
2. `BOOT_COMPLETED` + `LOCKED_BOOT_COMPLETED`. Restore alarms after
   reboot (AlarmManager state is wiped).
3. `MY_PACKAGE_REPLACED`. Restore after app upgrade.
4. `TIMEZONE_CHANGED`. Recompute fire times.
5. App foreground (`Activity.onResume` of `MainActivity`). Cheap
   idempotent safety net for any of the above that fired while we
   were not running.

`ReminderScheduler.rescheduleAll()` is idempotent. It builds the
canonical set of (eventId, reminderMinutes, instanceStartMillis)
tuples for the next 30 days, diffs against the set of currently
scheduled `PendingIntent`s, cancels removed ones, schedules new
ones. Bounded to 30 days so we do not pre-schedule a year of
alarms.

### Recurring event handling

For each recurring series in the 30-day window:
- Expand instances via `CalendarContract.Instances` query (the
  same path Asala already uses for read views).
- Skip cancelled exception instances
  (`Instances.STATUS == STATUS_CANCELED`).
- Skip instances whose start is in the past (a known
  late-firing root cause).
- Schedule only the next non-cancelled, non-past instance per
  series. After that fires, the `ContentObserver` triggers a
  reschedule and we pick up the next one.

### All-day event reminders

A reminder on an all-day event fires at **09:00 local** on the
offset day. Implementation:

```kotlin
fun computeAlarmTimeMillis(event: EventItem, minutesBefore: Int, zone: ZoneId): Long {
    return if (event.allDay) {
        val date = Instant.ofEpochMilli(event.startMillis).atZone(zone).toLocalDate()
        val offsetDate = date.minusDays(minutesBefore / 1440L)
        offsetDate.atTime(9, 0).atZone(zone).toInstant().toEpochMilli()
    } else {
        event.startMillis - minutesBefore * 60_000L
    }
}
```

For "at time of event" (`minutesBefore = 0`) on an all-day event,
the alarm fires at 09:00 day-of, not 00:00. Matches the common
convention in other calendar apps.

### DST / timezone correctness

- Event times are stored UTC in the provider; the scheduler reads
  them and converts to `ZoneId.systemDefault()` at fire-time
  computation. DST shifts that occur between schedule and fire are
  picked up by the next `ContentObserver` or app-foreground
  reschedule.
- `TIMEZONE_CHANGED` triggers an explicit `rescheduleAll()` for
  the case where the user travels.

| Manufacturer | Intent target |

| Xiaomi | `com.miui.securitycenter/.permission.AutoStartManagementActivity` |
| OnePlus | `com.android.settings/.Settings$HighPowerApplicationsActivity` (matches OnePlus's surface) |
| Huawei | `com.huawei.systemmanager/.appcontrol.activity.StartupAppControlActivity` |
| Oppo | `com.coloros.safecenter/.permission.startup.StartupAppListActivity` |

Each intent is wrapped in a `try/catch (ActivityNotFoundException)`

## Data flow

```
Event editor save with reminder
  -> RemindersRepository.setReminder (writes CalendarContract.Reminders)
  -> ContentObserver on Reminders.CONTENT_URI fires
  -> ReminderScheduler.rescheduleAll()
  -> AlarmManager.setExactAndAllowWhileIdle for the next 30-day window

Alarm fires
  -> ReminderAlarmReceiver.onReceive
  -> Read event, calendar color, location
  -> NotificationManagerCompat.notify(eventId.toInt(), notification)
  -> CalendarAlerts row: STATE = STATE_FIRED

User taps notification body
  -> PendingIntent for MainActivity with NOTIF_OPEN_EVENT extra
  -> MainActivity routes to AppViewModel.openEventDetail(eventId, instanceMillis)

User taps Snooze action
  -> PendingIntent for NotificationActionReceiver
  -> If session-cached snooze choice: snooze directly
  -> Else: launch SnoozePickerActivity
  -> Picker writes new CalendarAlerts row + reschedules + dismisses notification

User taps Dismiss action
  -> PendingIntent for NotificationActionReceiver
  -> CalendarAlerts row: STATE = STATE_DISMISSED
  -> notification cancelled
```

## Testing strategy

Tests verify intent (CLAUDE.md rule 7). Each test names the
business reason for the assertion.

### JVM unit tests (`app/src/test/`)

- `ReminderAlarmTimeMathTest.kt`
  - Timed event, "10 min before": `triggerAt == startMillis - 600_000`.
  - All-day event, "at time of event": `triggerAt == localDate(start).atTime(9,0)`.
  - All-day event, "1 day before": `triggerAt == localDate(start).minusDays(1).atTime(9,0)`.
  - DST spring-forward boundary, all-day "9am day of": fires at the
    correct wall-clock 09:00, not 08:00 nor 10:00.
  - DST fall-back boundary, same.
- `ReminderSchedulerDiffTest.kt`
  - rescheduleAll is idempotent: running twice produces the same
    set of PendingIntents.
  - Adding a new reminder schedules exactly one new alarm.
  - Removing a reminder cancels exactly the matching alarm.
  - Cancelled recurring exception instance is skipped.
  - Past-start instances are skipped.
  - Same alert row is never scheduled twice.

### Integration / instrumented tests (optional in v0.7, document as M5)

- Boot-rescheduled alarm fires within 30 seconds of expected time
  on a real device.
- Permission denial path renders the banner and offers re-prompt.

### Manual verification (paired phone)

All manual verification starts from a fresh install (uninstall first; permissions-already-granted devices hide bugs in the permission-gated flow).

   - From a fired notification, tap Snooze.

## Performance budget

- `ReminderScheduler.rescheduleAll` must complete in under 200ms
  for a calendar with up to 1000 upcoming reminders in the 30-day
  window. Measured via a JVM benchmark in the test suite. Above
  that, we slice the work onto `Dispatchers.IO` with explicit
  yielding.
- Notification post latency: not user-visible since `AlarmManager`
  fires the receiver, but the receiver must complete in under
  10s (Android receiver timeout). Realistic worst case: ~50ms.

## Privacy

- No new data leaves the device. The notification content is
  read from the provider and posted to the local notification
  manager. No cloud, no telemetry.
- The OEM advisory does not collect or transmit anything; it only
  reads `Build.MANUFACTURER` and shows a dialog.
- Permission set additions: `USE_EXACT_ALARM` (no PII), `SCHEDULE_EXACT_ALARM` (no PII), `RECEIVE_BOOT_COMPLETED` (no PII).
  `POST_NOTIFICATIONS` already declared.
