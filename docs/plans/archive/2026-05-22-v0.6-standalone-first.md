## Context

The user asked: "I'd like the ability for Asala to be a standalone local
calendar if someone wants where it doesn't have any dependencies on
anything else, but could be connected via CalDAV if wanted." Plus a
prioritized request for the easiest items across the roadmap.

Verified state before planning:

- Asala already runs fully offline against the Android Calendar Provider
  with `READ_CALENDAR`, `WRITE_CALENDAR`, `POST_NOTIFICATIONS` only. No
  network permission. Local-account calendars (`ACCOUNT_TYPE = "LOCAL"`)
  are detected and labeled in the drawer.
- Asala does NOT currently expose UI to **create** a local calendar.
  Users have to use another calendar app or system Settings once to seed one.
- Polish bugs N7 and N8 were already fixed in commit `a7abc9c` (the
  notes weren't updated). Dropped from scope.

## Scope (four items + one docs sweep)

### Item 1: Wong / Okabe-Ito color-blind-safe palette default

Replace the 8 hex colors in the local-calendar color picker
([CalendarDrawer.kt:227-234](../../app/src/main/kotlin/com/arishawke/asala/calendar/ui/month/CalendarDrawer.kt#L227-L234))
with the [Okabe-Ito 8-color palette](https://jfly.uni-koeln.de/color/)
(the Nature Methods recommendation, also called Wong palette after the
2011 paper). The current palette is generic brand colors that fail
deuteranopia / protanopia disambiguation.

New palette (sRGB hex):
```
0xFF000000  // black       (replaces an existing color or kept for default)
0xFFE69F00  // orange
0xFF56B4E9  // sky blue
0xFF009E73  // bluish green
0xFFF0E442  // yellow
0xFF0072B2  // blue
0xFFD55E00  // vermillion
0xFFCC79A7  // reddish purple
```

Note: black is intentional in the Okabe-Ito set, but is a poor choice
as an event color (renders as the chip background's outline against
dark themes). Swap it for a neutral grey: `0xFF999999`.

Files: `CalendarDrawer.kt` only.

### Item 2: DAVx⁵ pointer in Settings

For CalDAV sync today (Nextcloud, Fastmail, mailbox.org, posteo,
Disroot, self-hosted Radicale), the FOSS-Android convention is to
register the CalDAV server through [DAVx⁵](https://www.davx5.com/) (the
open-source CalDAV/CardDAV sync provider, formerly DAVdroid). DAVx⁵
exposes the synced calendars to the system Calendar Provider; Asala
picks them up automatically with no code change here.

The roadmap mentions building CalDAV ourselves via ical4j-android; that
remains a deferred multi-week project. The cheap shippable now is a
Settings card that:

1. Says "Sync with a CalDAV server (Nextcloud, Fastmail, etc.) using
   DAVx⁵, an open-source companion app."
2. On tap: launch DAVx⁵ if installed (`Intent.ACTION_MAIN` on
   `at.bitfire.davdroid`); otherwise open F-Droid / Play Store at
   that package.

Implementation outline:

- New section header in `SettingsScreen.kt`: "Sync".
- Single row, similar style to existing rows: title + supporting
  text + chevron.
- Click handler that tries `packageManager.getLaunchIntentForPackage("at.bitfire.davdroid")`
  first, falls back to a market intent
  (`market://details?id=at.bitfire.davdroid`), and finally to F-Droid
  (`https://f-droid.org/packages/at.bitfire.davdroid/`).

Files:
```
ui/settings/SettingsScreen.kt     (add row + click handler)
res/values/strings.xml            (settings_section_sync,
                                   settings_davx5_title,
                                   settings_davx5_supporting)
```

No new Android permission needed; intents to other apps are free.

### Item 3: Create local calendar UI

Closes the standalone-first gap. Single dialog launched from one of:

- A "+" button in the drawer's calendar list header, OR
- A row in Settings under a new "Calendars" section.

Recommendation: **drawer header**, because the user's mental model for
calendar management is the drawer (they already see calendars there).
Settings row is the secondary path.

Dialog content:

- Name field (`TextField`, required, max ~50 chars)
- Color (the 8-color Okabe-Ito palette from Item 1, chip-row)
- Save / Cancel

Save action calls `ContentResolver.insert(CalendarContract.Calendars.CONTENT_URI, ...)`
with:

```kotlin
ContentValues().apply {
    put(Calendars.ACCOUNT_NAME, "Asala Local")
    put(Calendars.ACCOUNT_TYPE, CalendarContract.ACCOUNT_TYPE_LOCAL)
    put(Calendars.NAME, internalName)
    put(Calendars.CALENDAR_DISPLAY_NAME, userTypedName)
    put(Calendars.CALENDAR_COLOR, color)
    put(Calendars.CALENDAR_ACCESS_LEVEL, Calendars.CAL_ACCESS_OWNER)
    put(Calendars.OWNER_ACCOUNT, "Asala Local")
    put(Calendars.SYNC_EVENTS, 1)
    put(Calendars.VISIBLE, 1)
}
```

The insert URL must include `CALLER_IS_SYNCADAPTER=true` plus the
account name/type as query params, per the Android Calendar Provider
contract (this is required for any provider write that creates a
calendar). Reference: [CalendarContract.Calendars docs](https://developer.android.com/reference/android/provider/CalendarContract.Calendars).

Files:
```
ui/calendar/CreateCalendarDialog.kt   (new — composable)
ui/calendar/CreateCalendarDialog.kt   contains dialog + state
data/CalendarRepository.kt            (add `createLocalCalendar(name, color)` method)
ui/month/CalendarDrawer.kt            (add "+" affordance to header)
res/values/strings.xml                (~6 new strings)
```

Test: create a calendar, verify it appears in the drawer, create an
event in it, verify the event shows up.

### Item 4: Event search

User-facing search for events. Design defaults (decided here; flag for
user review):

- **Search fields:** title, location, description (the common
  default behaviour).
- **UI entry:** a search icon in the top app bar's action area
  (alongside Today / Settings). Tapping it opens a dedicated
  `SearchScreen` (full-screen, like Settings).
- **Search field:** Material 3 `SearchBar` at the top with a text
  field and a leading back icon.
- **Results:** `LazyColumn` grouped by date, similar to Schedule view.
  Each row tappable to open the event detail sheet.
- **Recurrence:** each upcoming instance is a separate result row
  (matches the `Instances` query's behaviour). Past instances also
  searchable.
- **Range:** from one year ago to two years ahead (matches `Schedule`
  view's window scaled up). Could be made configurable later.
- **Empty state:** "No matching events" when query yields zero rows.
- **Debounce:** 200ms keystroke debounce so typing doesn't fire a
  query per character.

Implementation outline:

```
ui/search/SearchScreen.kt              (new — top-level composable)
ui/search/SearchViewModel.kt           (new — query flow, debounce,
                                        Instances query, calendar
                                        filter)
data/EventRepository.kt                (add `searchEvents(query, range)`
                                        method; existing observeEvents
                                        can be reused with a content
                                        filter)
res/values/strings.xml                 (search_hint, search_no_results,
                                        action_search, cd_back)
MainActivity.kt                        (wire toolbar Search action +
                                        navigation to SearchScreen)
```

Query strategy: use `CalendarContract.Instances.query` (which Asala
already uses) with a `selection` clause:

```
"((${Events.TITLE} LIKE ?) OR (${Events.EVENT_LOCATION} LIKE ?) OR (${Events.DESCRIPTION} LIKE ?))"
```

with `selectionArgs = arrayOf("%$q%", "%$q%", "%$q%")` (parameterized
to prevent injection). Filter against `hiddenCalendarIdsFlow` in the
ViewModel.

Recurrence handling: the `Instances` table already returns one row per
occurrence, so no extra work. `instanceMillis = begin` flows into the
event detail sheet as it does from other views.

Accessibility: search bar gets `contentDescription = stringResource(R.string.cd_search_field)`;
the screen has its own back button (TalkBack-reachable).

Test: search "design"; results show events with "design" in title or
notes; tap a result; detail sheet opens correctly; back returns to
search results; back again exits search.
